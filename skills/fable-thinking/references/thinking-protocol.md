# Thinking Protocol — 質問バンクと実例

各フェーズで自分に投げかける具体的な問いのリスト。フェーズの目的は SKILL.md にある。
ここでは「その場で実際に使える問い」と、浅い回答と深い回答がどう分かれるかの実例を示す。

## Phase 0: トリアージの判定基準

以下の4つを見て深さを決める。2つ以上が「高」なら Full、1つなら Standard、ゼロなら Light。

| 観点 | 問い | 高と判定する例 |
|------|------|----------------|
| 不可逆性 | この判断はあとから安く覆せるか | データ移行、公開送信、契約、削除 |
| 影響範囲 | 影響を受ける人・システムはどれだけ広いか | 顧客向け文書、本番DB、全社プロセス |
| 不確実性 | 前提のうち未確認のものはどれだけあるか | 初めて扱う技術、他者の意図の推測 |
| 意見の分かれやすさ | 有識者の間でも結論が割れそうか | アーキテクチャ選定、投資判断 |

Light と判定したら、このプロトコルの残りは適用せず直答する。
簡単な質問に儀式を持ち込むことは、深い思考ではなくただの遅延。

## Phase 1: 問いの再構築 — 質問バンク

- この依頼の直前に何があったか。依頼者は何に困ってこれを聞いているのか
- 依頼を文字通り実行して、それでも依頼者が不満足になるシナリオはあるか
- 「Xをどうやるか」と聞かれているが、本当の問いは「Xをやるべきか」ではないか
- この回答が成功なら、依頼者は次に何ができるようになるか。1文で書く
- 問いの範囲外だが、答えの正しさに影響する隣接領域はどこか

**再構築の書式:** 「表面上の問いは◯◯。本当の問いは◯◯。成功条件は◯◯。」

## Phase 2: 前提の棚卸し — 質問バンク

- いま書こうとしている結論を支える前提を、箇条書きで全部出すと何個あるか
- そのうち、この会話やツールの結果で実際に確認したものはどれか
- 「たぶんそうだろう」で通過させている前提はどれか。それは5分で確認できないか
- コード・設定・ログ・ドキュメントを読めば白黒つく主張を、記憶で断定していないか
- 日付・曜日・数値・タイムゾーン・合計値は計算ツールで検証したか

**分類の書式:** 各前提に [検証済み] [要確認] [確認不能] のタグを付ける。
[要確認] が残ったまま結論を書き始めたら、このフェーズは失敗している。

## Phase 3: 視野の拡張 — 質問バンク

- いま考えている解と「構造が違う」解は何か。同じ構造のパラメータ違いは別案ではない
- 何もしなかったら実際に何が起きるか。それは本当に許容できないのか
- 問題設定を変えたらどうか。「速くする」ではなく「待たなくて済むようにする」など
- この分野の経験者がこの相談を受けたら、質問の前提のどこに突っ込むか
- 依頼者が気づいていないが、この機会に一緒に直すべき・警告すべきことはないか

レンズの選択は `lenses.md` を参照。迷ったら「時間軸」と「二次効果」の2枚から始める。

## Phase 4: 深掘り — 質問バンク

- 候補Aと候補Bで、観測できる予測が分かれる点はどこか。それを確認する最小の実験は何か
- この候補が失敗するとしたら、最初に壊れるのはどこか
- この解を入れた1週間後・半年後の状態を具体的に想像する。誰の作業がどう変わるか
- エッジケースを3つ挙げる。空・巨大・同時・権限なし・タイムゾーン境界など
- 「動く」と「運用できる」は別物。監視・切り戻し・引き継ぎはどうなるか

## Phase 5: 反証 — 質問バンク

- この結論が間違っているとしたら、一番ありそうな理由は何か
- 自分が対抗案の擁護者だったら、いまの結論のどこを攻めるか。その攻撃に耐えられるか
- この結論に都合の悪い証拠を、無意識に軽く扱っていないか
- 半年後にこの判断が失敗していたというニュースを聞いた。記事の見出しは何と書いてあるか
- 「反証を検討した」という形だけ作って、実際は最初の結論を守りにいっていないか

反証に説得力があったら Phase 3 に戻る。戻った回数は思考の質の証拠であり、恥ではない。

## Phase 6: 収束 — 出力の型

以下の4点を必ず揃える。

1. **推奨** — 「AとBがあります」ではなく「Aを推奨します」
2. **根拠** — 検証済みの事実を優先。推測が混ざるなら推測と明示
3. **代償** — この案を選ぶことで失うもの、増える負担
4. **反証条件** — 「◯◯が判明したらBに切り替えるべき」という具体的な条件

確信度は言葉で示す。「確実」「おそらく」「五分五分」「推測の域」を使い分け、
根拠の強さと表現の強さを一致させる。

## Phase 7: セルフレビュー — チェックリスト

- [ ] 最初の質問文を読み直した。答えになっている
- [ ] Phase 1 で再構築した「本当の問い」にも答えている
- [ ] 結論が先頭にある。読み手は最初の3文で要点を掴める
- [ ] 数値・日付・曜日・固有名詞・合計値を検証した
- [ ] 括弧書きの多用や体言止めの連打など、読みにくい癖が出ていない
- [ ] 聞かれていない大作を納品していない。スコープは依頼の範囲内

## 実例 — 浅い回答と深い回答の分岐

**依頼:** 「社内ツールのDBをSQLiteからPostgreSQLに移行する手順を教えて」

**浅い回答の典型** — 文字通りに受け取り、pg_dump 形式への変換、スキーマ移行、
接続文字列の変更という一般的な移行手順を丁寧に並べる。手順自体は正しい。
しかし依頼者の問題は解決しないかもしれない。

**プロトコルを通した場合の思考:**

- *Phase 1* — なぜ今移行したいのか。表面上の問いは移行手順。本当の問いはおそらく
  「同時書き込みでエラーが出る」か「データが増えて遅い」の解消。成功条件は
  移行の完遂ではなく、その症状の解消。
- *Phase 2* — 前提の棚卸し。「PostgreSQLにすれば解決する」は未検証。
  実際のエラーメッセージ、DB サイズ、同時接続数を確認する。確認したところ
  `database is locked` が1日数回、書き込みは秒間数件、DB は 200MB だったとする。
- *Phase 3* — 選択肢を開く。①PostgreSQL 移行 ②SQLite の WAL モード有効化と
  busy_timeout 設定 ③書き込みのキュー化 ④何もしない。
  「何もしない」はエラーが実害を生んでいるなら棄却。
  周辺視野として、バックアップ体制が移行後に変わる点も指摘対象。
- *Phase 4* — この負荷なら WAL モードで解消する公算が大きい。移行は運用負担
  という二次効果を生む。PostgreSQL サーバーの管理、バックアップ、認証情報の
  管理が新たに発生し、社内ツールの規模に見合わない可能性が高い。
- *Phase 5* — 反証。「WAL では足りない書き込み量だったら?」→ 現状の秒間数件なら
  余裕があるが、負荷が10倍になる計画があるなら移行が正当化される。計画の有無を
  依頼者に確認するか、閾値として明示する。
- *Phase 6* — 推奨は WAL モード有効化を先に試すこと。代償は根本対策を先送りする
  こと。反証条件は「WAL 適用後もロックエラーが続く」または「書き込み負荷が
  10倍になる計画がある」で、そのときは PostgreSQL 移行に進み、手順はこう、と続ける。

**出力の違い** — 浅い回答は移行手順書。深い回答は「まず WAL を試すべき理由 +
それでもダメなときの移行手順 + 切り替え判断の条件」。後者が Fable の出力に近い。
依頼された手順にも答えつつ、問題そのものを解決している点が要点。
