# 日本語中心の試運用・校正計画

## この配布時点で分かること

コードのオフライン試験は、APIの形・集計・引用対応・保留・比較の実装を確認したもの。
実APIによる日本語の判断精度、英語との同等性、運用上の誤指摘率は確認していない。
Jevは英語が主要学習言語で、非英語は自分の文章で試すよう公式が案内している。[1]

ここで測るのは「AI製かどうか」ではなく、「編集上の指摘が妥当で、直すと読み手の役に立つか」。
作者が人間かAIかのラベルは目標値に使わない。

## 最初のパイロット

以下の件数は運用開始用の提案であり、統計的な十分性を保証する数字ではない。
まず許可済みの日本語80件程度・英語20件程度を集め、少なくとも2名が独立に評価する。
本番ゲートを設定したい場合は、文書・案件・作者単位でtrain/dev/testを分け、評価用データを増やす。
同じ文章の改稿前後を別splitへ分散させない。

日本語は顧客メール、社内チャット、提案書、報告書、仕様書、短文、正式文書を含める。
自然だが定型的なメール、見出しの多い良い仕様書、敬語の多い適切な社外文も十分入れる。
英語は非母語話者の自然な業務文、形式的な依頼、技術資料、短文を含め、流暢さと作者を結び付けない。

`examples/pilot_cases.jsonl`は合成の境界ケース30件（日本語20、英語10）。
`intended_check`は設計意図であり、測定済みの正解・人間の合意ラベルではない。
実運用の精度を主張するためのテストセットとして単独で使わない。

## 人が付けるラベル

軸ごとの適用可否、深刻度0〜4、指摘を裏付ける原文範囲、修正すると有益かを評価する。
修正文は内容保持を別ラベルで評価し、意味・数値・条件が変わったら文体改善とは分けて記録する。
2名で不一致の例は擦り合わせ、特に「業務上の定型であり問題ない」境界をrubricへ追加する。

採点画面には出力元モデルや執筆者情報を見せない。改稿前後を比べる際はA/Bの順序も入れ替える。

## 測定項目

文書種別と言語ごとに、以下を分けて見る。

| 指標 | 意味 |
|---|---|
| 指摘precision | 人が有益と判断した指摘 / 自動的に返した指摘 |
| 正常文への過剰指摘率 | 正常と合意された文章のうち、不必要な修正を要求した割合 |
| 保留率 | 指数保留または軸保留の割合。低いほど良いとは限らない |
| 根拠妥当性 | 選ばれた引用が、その問題を実際に示す割合 |
| 順序一致 | 人がより適切と判断した改稿と、指数差の方向が一致する割合 |
| 内容保持率 | 改稿後も事実・数値・要件・条件が保持された割合 |
| 人同士の一致 | 軸の曖昧さ自体を見つける。必要なら重み付きκ等を用いる |

confidenceは分布統計であり、人の判断との較正は自動的には保証されない。[2]
モデルのconfidenceとseverityの閾値は役割が違うため、それぞれdevデータで調整する。
日本語と英語、emailとtechnicalで同じ閾値を強制しない。未評価の組合せは人確認を残す。

## 本番運用での変更管理

固定モデルID、rubric.jsonのハッシュ、profile、言語、briefの作り方を記録する。
モデル更新、ルーブリック変更、抽出器変更、対象部署の変更は再校正の契機にする。
同じbriefや原文でも判断が揺れ得るので、少数の固定golden setを繰り返し評価する。

当初は影の評価として記録し、作成者の承認なしに修正・差し戻し・人物評価へ使わない。
自動化を増やす前に、高precisionの狭い指摘から適用し、不必要な全面改稿が起きないか監査する。
